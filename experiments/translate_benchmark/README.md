# 翻譯模型實測：本機 Ollama 上的 5 個模型

> 暫時性實驗，不屬於正式程式碼。日期：2026-11-05。規格：`docs/specs/translate.md`。

## 環境

- GPU：NVIDIA GeForce RTX 5070（12 GB）；同時有其他工作佔用部分 VRAM（量測時 VRAM 用量 10–11.6 GB），因此**換模型的載入時間**會偏長，但每句的推論延遲不受影響。
- Ollama 0.40.14，OpenAI 相容 API（`/v1/chat/completions`，SSE 串流）。
- 用 `kikitori.translate.OpenAICompatibleTranslator`（正式程式碼）送請求；`convert_to_traditional=False` 以量到模型原始輸出，再另外套用簡轉繁。

## 怎麼重跑

```text
uv run python -I -X utf8 experiments/translate_benchmark/menu.py
```

互動選單：1) 列出本機模型　2) 對所有有預設組的模型執行實測　3) 選一個模型　4) 顯示已存的摘要。結果存在 `results/<模型>.json`（每句的原文、原始輸出、轉換後輸出、首字延遲、總延遲、簡體字）。`-X utf8` 是讓輸出導到檔案或管線時不受 Windows 主控台編碼影響。

## 測試句

`lines.json`，全部自寫：

- 日文 22 句（VTuber 直播、戰鬥、校園、日常；含「草生えるｗｗｗ」「推しが尊すぎて無理」「スパチャ」等網路用語）。
- 英文 11 句（直播用語、劇情、日常）。
- 中文 → 日文 3 句、中文 → 英文 3 句（口譯模式）。
- 同一場景的句子依序翻譯，前兩句原文放進 `context`（模型支援前文時）。

量測方式：每個模型先暖機一句（載入模型，不計時）；之後每句用 `stream()`，**首字延遲** = 送出請求到第一次產出可顯示的譯文，**總延遲** = 到串流結束。

## 結果（最終設定）

| 模型 | 成功 | 錯誤 | 首字中位數 | 首字 P90 | 總延遲中位數 | 總延遲 P90 | 原始輸出含簡體（句） | 簡轉繁後含簡體（句） |
|---|---|---|---|---|---|---|---|---|
| `qwen3.5:9b` | 39 | 0 | 0.10 s | 0.13 s | 0.23 s | 0.26 s | 0/33 | 0/33 |
| `qwen3.5:4b` | 39 | 0 | 0.09 s | 0.12 s | 0.17 s | 0.21 s | 0/33 | 0/33 |
| `hy-mt1.5-7b:latest` | 39 | 0 | 0.05 s | 0.07 s | 0.20 s | 0.28 s | 0/33 | 0/33 |
| `hy-mt1.5-1.8b:latest` | 38 | 1 | 0.04 s | 0.06 s | 0.11 s | 0.15 s | 0/32 | 0/32 |
| `hf.co/SakuraLLM/Sakura-GalTransl-7B-v3:IQ4_XS`（只做日翻中） | 22 | 0 | 0.04 s | 0.06 s | 0.12 s | 0.16 s | 22/22 | 0/22 |

- 「含簡體」只算目標為 zh-TW 的句子；判斷方式同 `postprocess.simplified_characters`（OpenCC `s2tw` 會改、且不在 Big5 字集的漢字）。
- HY-MT 1.8B 的 1 個錯誤：「草生えるｗｗｗ」陷入一直輸出 `w`，Ollama 以一筆 `model:""` 的空片段結束串流（沒有 `finish_reason`、沒有 `[DONE]`），翻譯器回報 `TranslationResponseError`。用 curl 直接打同一個請求 4 次重現 1 次，是 Ollama 端的行為。
- 載入（暖機）時間：1.5–18 秒，視 VRAM 是否要先卸載其他模型而定。

## 過程中發現並修正的問題

### 1. `localhost` 每個請求多 2 秒（已修）

第一輪所有模型的首字延遲都是 **2.06–2.10 秒**，與模型無關。原因：Windows 上 `localhost` 先解析成 `::1`，Ollama 只聽 `127.0.0.1`，Python 依序嘗試位址時被拒的 IPv6 連線要約 2 秒才失敗（`socket.create_connection(("localhost", 11434))` 實測 2.059 s，`127.0.0.1` 為 0.000 s；curl 有 Happy Eyeballs 所以只多 0.2 s）。
修正：翻譯器對 `http://localhost` 先連 `127.0.0.1` 再試 `::1`，`Host` 標頭不變。修正後首字延遲降到 0.04–0.10 秒。單元測試 `test_localhost_prefers_ipv4_and_keeps_host_header` 鎖住這個行為。

### 2. HY-MT 把前文一起翻出來（改為不帶前文）

用官方 contextual 範本（前文 + 「参考上面的信息…注意不需要翻译上文」）時，HY-MT 1.8B 會把前文、甚至指令本身一起輸出，例如：

> 不要害怕……一點也不可怕！ / 咦，真的嗎？那不是很危險嗎？ / 參考上面的信息，將下面的文本翻译成繁體中文。…

另做的探測（6 組前文 × 2 次，判定「輸出含換行、指令或前文開頭」為失敗）：

| 範本 | HY-MT 1.8B | HY-MT 7B |
|---|---|---|
| 官方 contextual | 11/12 失敗 | 0/12 |
| 官方 contextual（前文後空一行） | 6/12 | 0/12 |
| 不帶前文 | 0/12 | 0/12 |

7B 在探測中沒問題，但在正式實測句組中重現了 1 次（ja17：把前一句「先輩、ちょっといいですか？」一起翻出來）。兩者都改為不帶前文（`supports_context=False`）。

### 3. Qwen3.5 9B 不翻譯、直接輸出日文（改用譯文語言寫指示）

第一版通用提示詞用英文寫規則，`qwen3.5:9b` 有 4/22 句直接輸出日文（例：「推しが尊すぎて無理…」→「推し尊すぎて耐えられない…」）。探測（6 句 × 3 次，輸出含假名即失敗）：

| 提示詞 | qwen3.5:9b | qwen3.5:4b |
|---|---|---|
| 英文規則（presence_penalty 1.5） | 11/18 | 2/18 |
| 英文規則（不送 presence_penalty） | 11/18 | 0/18 |
| 英文規則 + 最後一行寫明目標語言 | 6–10/18 | 0/18 |
| **繁體中文規則**（system + user 都用中文） | **0/18** | **0/18** |
| 繁體中文單一 user 訊息 | 0/18 | 0/18 |

所以通用提示詞的指示一律用譯文語言撰寫（zh-TW 用繁體中文、ja 用日文、en 用英文）。改完後正式實測 0/22 句輸出日文、0/33 句含簡體字。

### 4. 簡體字（加入 OpenCC，且只在有簡體字時才轉）

- Sakura 的官方提示詞就是「翻译成简体中文」，原始輸出 22/22 句是簡體；第一版英文提示詞下 Qwen 與 HY-MT 7B 也偶有個別簡體字（实、吗、赏）。
- 決定加入 **OpenCC 1.4.2**（Apache-2.0，官方 Python 套件，三平台都有 wheel），以 `s2twp`（台灣正體＋台灣慣用詞）轉換：Sakura 轉換後 0/22 句含簡體，且「视频」「软件」轉成「影片」「軟體」。
- 但 `s2twp` 會改壞已正確的繁體：「那個傢伙」→「那個傢夥」、「台灣」→「臺灣」；單字層級的 `s2t` 也會把「才、吃、伙」改成「纔、喫、夥」。所以**只有偵測到簡體專用字時才轉換**，簡體專用字定義為「OpenCC `s2tw` 會改、且不在 Big5 字集」的漢字（另加 `么于网扰`）。Big5 排除了兩岸通用字，第一版用 `s2t` 比對時誤判的才／吃／伙都不再算簡體。

### 5. 特殊 token 碎片（已修）

HY-MT 1.8B 偶爾在句尾輸出 `<|`（聊天範本特殊 token 的碎片）。後處理移除 `<|…|>` 與結尾的 `<|` 碎片。

### 6. 關閉 Qwen3.5 的思考

Qwen3.5 預設會思考。用 Ollama OpenAI 相容 API 的 `reasoning_effort: "none"` 關閉：未關閉時串流先送出大量 `delta.reasoning`（"Thinking Process: …"），關閉後首字延遲 0.09–0.10 秒、沒有推理內容。翻譯器也不讀 `delta.reasoning`，並移除內容裡的 `<think>…</think>`，作為其他服務的保險。

## 結論與推薦

| 可給翻譯的 VRAM | 即時（fast） | 完整（final） | 理由 |
|---|---|---|---|
| ≥ 7.5 GB | `qwen3.5:9b` | `qwen3.5:9b` | 品質最好；總延遲 P90 0.26 s，即時路徑也夠快 |
| 4–7.5 GB | `qwen3.5:4b` | `qwen3.5:4b` | 品質次之、3.3 GB |
| < 4 GB／沒有 GPU | `hy-mt1.5-1.8b` | `hy-mt1.5-1.8b` | 最小（1.9 GB）、最快；口語品質較差 |

- **即時與完整路徑用同一個模型**：GPU 上所有模型的總延遲都在 0.3 秒內，分開用兩個模型只會多佔 VRAM；Ollama 換模型要 1.5–18 秒，輪流使用反而更慢。
- **推薦預設**：快速與完整路徑都用 `qwen3.5:9b`（VRAM 不足時 `qwen3.5:4b`）。Apache-2.0、沒有地區限制。
- **HY-MT 1.5**：中→日／英好、延遲最低，但日文口語偏直譯，且授權不適用於歐盟、英國、南韓 → 當備選，`allow_restricted=False` 時排除。
- **Sakura-GalTransl**：日文動漫語氣最好，但 CC BY-NC-SA 4.0 非商用 → 不推薦為預設，只讓使用者自行選擇。
- 未實測：CPU 與 Apple Silicon 的延遲；長時間連續翻譯時的 VRAM 與 ASR 共用情形（留給 hardware／pipeline 里程碑）。
