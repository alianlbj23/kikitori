# 評測：Silero VAD 的重置策略

> 暫時性實驗，不屬於正式程式碼。日期：2026-11-05；Silero VAD v6.2.3（ONNX，`kikitori.vad.SileroVad`）、onnxruntime 1.31.1、Python 3.12。
> 規格：`docs/specs/vad-segmenter.md`「評測」一節。結論已寫回規格與 `ResetPolicy` 的預設值。

## 怎麼重跑

```text
uv run python -I experiments/silero_reset/menu.py
```

選單：`1. 下載 MUSAN`（約 11.09 GB，確認後才下載，可續傳）→ `2. 產生評測音軌` → `3. 執行評測` → `4. 離開`。
結果寫入 `data/results.md`（彙總、明細、前文對照）與 `data/results.json`。`data/` 已被 git 忽略。

## 素材與音軌版本

- **人聲**：`experiments/pipecat_vad/data/tracks/` 的動漫、VTuber 音軌（各 6 段、共 12 段，權利屬原權利人，只在本機）。
- **兩種版面**：
  - `original`：原本的版面，句間 0.15–1.5 秒。
  - `longgap`：同一批片段重新排列，句間 3–4 秒（保留 0.15、0.5 秒兩個短間隔）。原版面最長間隔 1.5 秒，加上 0.6 秒句尾停頓仍屬於句子，(c) 的 2 秒非人聲重置根本不會發生，必須另做長間隔版面才比得出差異。
- **背景**：白噪音、粉紅噪音（固定種子）；MUSAN 音樂依 `ANNOTATIONS` 的 vocals 欄分成「有人聲演唱」（`music_vocal`）與「純音樂」（`music_inst`）。每首取 8 秒（從 30 秒處起，避開前奏）串成一條背景。
- **兩種混法**：間隔填入（只換句間靜音，背景音量以 SNR 10 dB 計）；人聲底下疊加（SNR 20／10／5 dB，人聲功率只算正確區間內）。
- **設定**：(a) `a_stream_start`、(b) `b_after_utterance`、(c) `c_after_long_non_speech`（2.0 秒），以及前文對照 `a_no_context`（(a) + `context_samples=0`）。其餘參數皆為規格預設值（門檻 0.5／0.35、`min_speech_ms` 250、`pre_roll_ms` 200、`pause_secs` 0.6、`max_secs` 10）。

### MUSAN 只完成部分下載

本次執行時 OpenSLR 主站與三個鏡像站速度大多只有 0.01–0.2 MB/s（偶爾回到約 2 MB/s），11.09 GB 無法在本次工作時間內下載完。已下載的前段只包含 `music/`（fma、fma-western-art、hd-classical 共約 196 首），**還沒有 `noise/`**。因此：

- MUSAN 音樂版本：用一次性的腳本從部分壓縮檔取出完整的音樂檔（同樣套用 `tarfile` 的 `data` 過濾器、丟掉最後一個不完整的檔案），呼叫 `evaluate.py` 的同一套函式產生音軌與評測，結果在 `data/results_musan_partial.*`。
- 因為「可用檔案數」會影響固定種子挑到哪些曲子，另用三組種子（20261105／06／07）重複音樂版本，確認結論不是單一曲目組合造成的（`data/results_music_seeds.json`）。
- **MUSAN 雜音（`noise/`）版本尚未評測**。下載可續傳：在選單選 1 會從 `data/musan.tar.gz.part` 接著下載，完成後選 2、3 即可產出完整的指標表。

種子 20261105 用到的曲目：`music_vocal` = fma-0065、0019、0024、0097、0007、fma-wa-0026；`music_inst` = fma-0004、hd-0026、fma-wa-0008、0043、0046、0016。

### 其他檢查

- **原始動漫、VTuber 音軌**：三種策略都抓到全部 12 段（漏抓 0/12）。
- **純噪音音軌**：白噪音、粉紅噪音（−30／−15 dBFS，靜音與噪音交錯 30 秒）三種策略都產生 0 句（`tests/test_vad_integration.py`）。
- **前文對照**：68 條音軌全部判定「機率異常偏低」。接 64 樣本前文時人聲區平均機率 0.339–0.853；不接前文時最高只有 0.0021，所有音軌都 0 句、12/12 漏抓。與官方 issue #771 描述的「約 0.001」一致。
- **推論時間**：每個 32 ms 視窗平均 0.20 ms（204 次執行平均；單次執行最高 0.25 ms），低於 1 ms 的目標。
- **提早切斷**多半來自片段內部本來就有 ≥ 0.6 秒的停頓（原始音軌各策略都是 4 次），與重置策略無關；它反映 `pause_secs` 的取捨，不在本評測範圍。
- 逐格漏報率在乾淨音軌也有約 23%：正確答案以「整個片段」為人聲區間，片段內的換氣、停頓與字尾都算人聲。

## 結論：預設 `ResetPolicy.AFTER_LONG_NON_SPEECH`（c）

- **(c) 整體最好**：全部音軌的漏抓最少（35/408，(a) 42、(b) 46）、開始延遲最短（中位數 473 ms、P90 721 ms）、AUC 最高。優勢集中在「長間隔 + 音樂」：句間 3–4 秒都是音樂時，(a) 的狀態被音樂帶偏，下一句開頭的機率被壓低，漏抓與延遲都變多（純音樂 longgap：(a) 9/48、P90 1211 ms → (c) 2/48、713 ms；換兩組曲目重複仍是 13/96 → 7/96）。這與 pipecat #6207 描述的「音樂之後的語音被低報」相符。
- **在沒有長間隔的情況 (c) 等於 (a)**：原始版面幾乎不觸發重置（重置次數 0–3），乾淨語音的結果完全相同。
- **(b) 不採用**：每句結束立刻重置，下一句開頭剛好落在模型重新暖機的期間，乾淨與噪音音軌的開始延遲 P90 從約 0.6 秒拉長到 1.2–1.5 秒，噪音 original 版面漏抓 16/96（(a)(c) 為 9/96）。它在長間隔純音樂下表現好（1/48），但 (c) 也接近（2/48），且 (c) 不會傷害一般情況。
- **代價**：白／粉紅噪音的長間隔版面，(c) 漏抓 12/96、(a) 10/96，多 2 段；重置剛好落在語音開頭前時，那一句的開頭會晚一點被確認（pipecat 回報約 1% 的句子晚 200–400 ms）。這在樣本量（每組 12 段）下屬於小差異，換到音樂背景的收益比較大，所以仍選 (c)。
- **限制**：人聲樣本只有 12 段、背景曲目每組 6 首；MUSAN 雜音尚未評測。完成 MUSAN 下載後應重跑一次；換 Silero 版本時也要重跑（規格「更新模型」）。
